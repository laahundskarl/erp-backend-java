# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

JDK 21+ is required. If more than one JDK is installed, `JAVA_HOME` may not point at a
compatible one (Spring Boot 4 needs 17+) — check with `"$JAVA_HOME/bin/java" -version` before
running the wrapper, and export a correct `JAVA_HOME` for the session if it's wrong.

```bash
./mvnw compile                 # compile only
./mvnw spring-boot:run          # run the app locally (auto-starts Postgres via compose.yaml)
./mvnw test                     # unit tests only (Surefire, *Test classes) — no Docker needed
./mvnw verify                   # unit + integration tests (Surefire + Failsafe, *IT classes) — needs Docker running
./mvnw test -Dtest=ClassName#methodName    # run a single test
./mvnw verify -Dit.test=ClassName#methodName -DfailIfNoTests=false   # run a single integration test
```

There is no linter/formatter configured (no Checkstyle/Spotless).

## Architecture

Package-by-feature, not by layer: `catalogitem`, `order`, `orderitem` each contain their own
entity, repository (+ QueryDSL custom impl), service, controller and `dto/` subpackage.
Cross-cutting error handling lives in `common/exception`; QueryDSL/OpenAPI bean config lives in
`config/`. See [README.md](README.md) for the full endpoint list and business-rules table —
don't duplicate that here, but the essentials future changes need to respect:

- `discountPercentage` on an `Order` can only change while `status == OPEN` (409 otherwise);
  it applies only to `OrderItem`s whose `CatalogItem.type == PRODUCT`.
- A `CatalogItem` referenced by any `OrderItem` can't be deleted (409).
- An `OrderItem` can't be created against an inactive (`active=false`) `CatalogItem` (409).
- Order totals (`OrderTotals`) are always computed from current items, never persisted.
- These are the only cross-entity rules; adding more (e.g. blocking item edits on a `CLOSED`
  order) would be scope creep — see the "Deliberately out of scope" note in the README.

Read-model split on `Order`: `GET /api/orders` (list) returns `OrderSummaryResponse`, built by a
QueryDSL projection with a correlated item-count subquery — **not** a fetch-joined collection —
specifically to keep `Pageable` doing a real SQL `LIMIT`/`OFFSET` instead of Hibernate paginating
an in-memory list. `GET /api/orders/{id}` (detail) loads the full entity and computes
`OrderTotals` from `order.getItems()`. If you touch order list/detail queries, preserve that
split rather than reintroducing a collection fetch-join under pagination.

### QueryDSL + Lombok build wiring (pom.xml)

Q-classes are generated by `querydsl-apt` (classifier `jakarta`, not the old `jpa` classifier —
this project targets `jakarta.persistence`, not `javax.persistence`). Because
`maven-compiler-plugin`'s `default-compile` execution sets an explicit
`annotationProcessorPaths`, automatic processor discovery is disabled, so **every** processor
needed at compile time must be listed there explicitly: `lombok`, `querydsl-apt` (jakarta
classifier), and `jakarta.persistence-api` (querydsl-apt needs the persistence annotations
themselves on its own processor path or it fails with `NoClassDefFoundError:
jakarta/persistence/Entity`). If you add a new annotation processor, it goes in that same list
or it silently won't run.

### Jackson 2 vs Jackson 3

Spring Boot 4 / Spring Framework 7 ship both `com.fasterxml.jackson` (2.x) and `tools.jackson`
(3.x, the renamed groupId) on the classpath. Spring MVC's message converters wire up a
`tools.jackson.databind.ObjectMapper` bean, not `com.fasterxml.jackson.databind.ObjectMapper` —
autowiring the wrong one fails with "No qualifying bean". See
`src/test/java/com/leonardo/erp/support/AbstractIntegrationTest.java` for the working import.

### Testcontainers: singleton pattern, not `@Testcontainers`/`@Container`

`AbstractIntegrationTest` starts one `PostgreSQLContainer` in a `static { }` block and never
stops it (Ryuk reaps it at JVM exit). It is deliberately **not** annotated with
`@Testcontainers`/`@Container` — that combination stops the container in `afterAll` of
whichever `*IT` class happens to run first, leaving every other integration test class stuck
retrying a dead connection for 30s before failing. `@ServiceConnection` still auto-wires the
datasource without needing the lifecycle annotations. Don't "simplify" this back to
`@Testcontainers`/`@Container` — it was tried and breaks multi-class runs.

Also note: within one `@Transactional` test method, saving an `OrderItem` from its own side of
the association does **not** update an already-loaded `Order.items` in the persistence context
(first-level cache returns the same Java object). Tests that need the server to see items added
"from the other side" call `entityManager.flush(); entityManager.clear();` before hitting the
endpoint — see `OrderControllerIT`. This isn't an issue in production, where each request is its
own transaction/persistence context.

### mvnw executable bit

`core.fileMode=false` is common on Windows git installs, so a local `chmod +x mvnw` can be lost
on commit. If CI fails with `./mvnw: Permission denied`, fix it in the index directly —
`git update-index --chmod=+x mvnw` — not just on the filesystem.

## Repository conventions (this repo specifically — overrides global defaults)

- **Commit trailers:** code commits do **not** get a `Co-Authored-By` trailer; documentation-only
  commits (README, `docs/`) do. This is the opposite of the global default and only applies here.
- **Language:** everything — code, identifiers, endpoints, Swagger, commit messages, docs — is
  US English.
- **Tone:** this repo is a public portfolio piece for recruiters, not a graded exercise. Don't
  reintroduce "assessment"/"Level III"/take-home-test framing into docs or commit messages.
- **`main` is protected:** a repository ruleset requires a pull request plus a passing `Build and
  test` CI check to merge, with no bypass actors — including the owner. Direct pushes to `main`
  will be rejected; always branch, push, and `gh pr create`, even for tiny fixes.
- **GitHub CLI auth:** `gh auth status` may show an *active* account authenticating via a
  `GITHUB_TOKEN` env var with narrower scopes than the keyring credential. If a `gh` operation
  fails on permissions (e.g. `repo create`, pushing to `.github/workflows/`), retry with
  `GITHUB_TOKEN` and `GH_TOKEN` unset so it falls through to the keyring credential (scopes:
  `repo`, `workflow`).
